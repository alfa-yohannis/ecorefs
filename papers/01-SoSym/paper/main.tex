\title[Decentralized Model Persistence]{Towards Decentralized Model Persistence}

\author*[1]{\fnm{Alfa} \sur{Yohannis}}\email{alfa.ryano@pradita.ac.id}
%% Further authors: \author[1]{\fnm{Given} \sur{Family}}\email{name@example.org}

\affil*[1]{\orgdiv{Department of Informatics}, \orgname{Pradita University}, \orgaddress{\city{Kabupaten Tangerang}, \state{Banten}, \country{Indonesia}}}

\abstract{Model persistence frameworks such as the Eclipse Modeling Framework (EMF) identify a model by a location, for example a file path. The content at a location can change while the location stays the same. The InterPlanetary File System (IPFS) identifies a file by a content identifier (CID) instead. The CID is computed from the file content, so every change to a model produces a new identifier. The paper examines the consequences for model persistence and for references between model resources. An EMF resource implementation saves models to a local IPFS node and loads the models back by CID. References can point to fixed CIDs or to mutable names of the InterPlanetary Name System (IPNS). A cascade save stores every resource with a reference to a changed resource again. IPFS support was also added to the Eclipse BPMN2 Modeler. A benchmark used generated models of 100 to 500,000 elements. A save through IPFS took 20 to 22~ms longer than a save to a local XML Metadata Interchange (XMI) file for models up to 10,000 elements, and the relative cost fell from about 31 times the XMI time at 100 elements to 1.4 times at 500,000 elements. A case study split 39 MoDisco models of the Eclipse Java development tools (1.04~GiB) into 6,933 resources and published the resources on IPFS. For eight components with 1,639 resources, EMF Compare found no differences between the local models and the copies fetched from IPFS.}

\keywords{Model-driven engineering, Model persistence, Eclipse Modeling Framework, IPFS, Content-addressed storage, Cross-resource references}

\section{Introduction}\label{sec:introduction}

Model-driven engineering (MDE) uses models to manage the complexity of platforms and to express domain concepts~\cite{schmidt2006mde}. MDE tools store models in files or in model repositories. The Eclipse Modeling Framework (EMF)~\cite{steinberg2008emf}, a software framework for implementing MDE, stores each model in a resource, and a Uniform Resource Identifier (URI) names the resource. Resources are usually serialized in the XML Metadata Interchange (XMI) format~\cite{omg2015xmi}. Common URIs such as \texttt{file://} and \texttt{platform://} name a location. The content at a location can change, but the URI stays the same. A reference to another resource therefore resolves to the current content at the location. The referenced model may have changed since the reference was created.

One example shows what the gap between a location and a version costs. A supplier and a buyer agree on a collaboration model in Business Process Model and Notation (BPMN)~\cite{omg2010bpmn}, where the collaboration refers to an order process and both models refer to a payment process of the supplier. Each reference is a file path with a fragment. After that, the supplier changes the payment process and saves the changed model at the same path. Every copy of the collaboration then resolves to the changed payment process, although the buyer agreed to the earlier version. Moreover, no reference records the agreed version, and no check reveals the change. The same three models return as a case study in Section~\ref{sec:evaluation-rq2}.

The gap appears in other modeling tasks as well. Teams keep models in shared folders or in model repositories, where several models often reference one metamodel or one shared library model~\cite{dirocco2015repositories,franzago2018collaborative}, so an edit to the shared resource changes what every referring model means. Reverse engineering gives a second setting, because MoDisco builds models of an existing code base~\cite{bruneliere2010modisco,bruneliere2014modisco}, and a later analysis should run on the same snapshot as an earlier analysis. Therefore, a model reference that names a version would remove the ambiguity in every case above.

Content-addressed storage takes a different approach. The InterPlanetary File System (IPFS) identifies content by a content identifier (CID)~\cite{benet2014ipfs,ipfsdocscid}. The CID is computed from the content, so a changed file receives a new CID~\cite{ipfsdocsipns}. Content under a given CID cannot change. In addition, any IPFS node with a copy of the content can serve the content~\cite{trautwein2022ipfs}. The InterPlanetary Name System (IPNS) adds mutable names on top of CIDs~\cite{ipfsdocsipns}.

Content addressing has two consequences for models. First, a reference to a CID pins the exact version of the referenced model, in the way that a lock file records the exact dependency tree of a project~\cite{npmpackagelock} and Nix derives unique component paths from cryptographic hashes~\cite{dolstra2004nix}. Second, every save of a model creates a new CID, so references to the model need a deliberate update, and tools need support for the update. Dependency updates are a known source of problems in software ecosystems~\cite{cox2019dependencies,decan2019ecosystems}. A CID is also a cryptographic hash, so a reader can check that fetched content matches the requested identifier wherever the content is stored. However, the properties have costs. Content stays available only while at least one node stores the content, and each resource is loaded as a whole, without the on-demand loading of database-backed persistence~\cite{pagan2015repository,daniel2017neoemf}.

The properties open several uses in model-driven engineering:
\begin{itemize}
\item Model versioning and reproducible evaluation. Every save produces a fixed snapshot under a new identifier, so a version history needs only a record of identifiers, and a paper or an audit can name the exact model behind a result~\cite{koegel2010emfstore,lamb2022reproducible}.
\item Traceability. A trace link that carries a CID names the exact version of the target, so the link still points at the reviewed version after the target evolves.
\item Preservation and less dependence on a central server. A published model stays readable while at least one node stores the content, and any node with a copy can serve the model~\cite{dicosmo2017heritage,kelly2016wayback}.
\item Deduplication and incremental publication. Identical content always receives the same CID, so an unchanged component keeps the CID of the previous publication (Section~\ref{sec:rq2-partitioned}).
\item Collaboration across organizations. Partners exchange models without agreed paths and without a shared namespace~\cite{dirocco2015repositories,franzago2018collaborative}.
\item Simple caching and offline reading. A cached copy never goes stale and serves the model without a network connection, because content under a CID cannot change.
\end{itemize}
The paper covers the persistence layer, the references between resources and the cost of both, while the uses above follow from the properties and stay outside the evaluation.

Content-addressed persistence also brings challenges, and the paper addresses four. First, a resource has no identifier before the first save, and every later save changes the identifier, so the persistence layer needs a lifecycle that the resource model of EMF does not expect (Section~\ref{sec:rq1}). Second, a reference by CID becomes outdated as soon as the target changes, so an upgrade needs a cascade of saves along the referencing resources (Section~\ref{sec:rq2}). Third, a load fetches a whole resource, so a large model needs a split into many resources together with a publication structure that keeps the parts connected (Section~\ref{sec:rq2-partitioned}). Fourth, the layer has to fit the existing EMF ecosystem, so file resources and IPFS resources share one resource set, and the editors keep the standard save and load actions (Sections~\ref{sec:rq1-differences} and~\ref{sec:tool}). Finally, partial loading inside a single resource stays open, and Section~\ref{sec:limitations} lists the remaining limits.

Research on model persistence has mainly addressed scalability~\cite{kolovos2013roadmap}. Database-backed solutions load parts of a large model on demand~\cite{pagan2015repository,daniel2017neoemf}. Beyond scalability, model versioning systems track changes between versions of a model~\cite{koegel2010emfstore,altmanninger2009survey}. However, none of the reviewed approaches stores EMF models on content-addressed storage (Section~\ref{sec:related}).

The paper studies content-addressed persistence for EMF with three research questions (RQ1 to RQ3):

The paper makes four contributions:

\item An EMF resource implementation for IPFS. The implementation saves models as XMI files on a local IPFS node and loads models by CID or IPNS name (Section~\ref{sec:rq1}).
\item A description of four strategies for cross-resource references on IPFS and a cascade save for references by CID (Section~\ref{sec:rq2}).
\item IPFS support in the Eclipse BPMN2 Modeler for BPMN diagrams and in the generated BPMN2 tree editor (Section~\ref{sec:tool}).
\item An evaluation with generated models and with large MoDisco models of Java code (Section~\ref{sec:evaluation}).
\end{itemize}

\section{Background}\label{sec:background}

\subsection{Model persistence in EMF}\label{sec:background-emf}

EMF defines metamodels with Ecore. Ecore is aligned with the core subset of the Meta Object Facility (MOF), called Essential MOF~\cite{steinberg2008emf,omg2016mof}. A \texttt{Resource} holds the root objects of a model, and a URI identifies the resource. A \texttt{ResourceSet} groups resources and resolves references between the resources. A resource factory registry maps a URI scheme or a file extension to a resource factory. A \texttt{URIConverter} opens input and output streams for a URI through a list of URI handlers~\cite{steinberg2008emf}.

XMI files use the Extensible Markup Language (XML). A reference to an object in another resource is serialized as a URI with a fragment, for example \verb|href="model.xmi#//Person"|. During loading, EMF creates a proxy object for such a reference. The proxy is resolved on first access, and the target resource is loaded when needed.

\subsection{Content-addressed storage with IPFS}\label{sec:background-ipfs}

Content addressing identifies data by a hash of the data. Merkle introduced hash trees for authentication~\cite{merkle1988signature}. Later, Venti used a hash of the block contents as the identifier of a block in archival storage~\cite{quinlan2002venti}. Similarly, Git stores every object under the Secure Hash Algorithm 1 (SHA-1) checksum of the object content~\cite{chacon2014progit}.

IPFS combines content addressing with a peer-to-peer network~\cite{benet2014ipfs}. Content is stored in blocks, and links between blocks form a Merkle directed acyclic graph (DAG)~\cite{benet2014ipfs}. Nodes locate content through a distributed hash table (DHT) based on Kademlia~\cite{maymounkov2002kademlia,psaras2020ipfs}. Studies describe the design and performance of IPFS~\cite{trautwein2022ipfs} and the size of the public network~\cite{henningsen2020mapping}. A survey also compares IPFS with other peer-to-peer data networks~\cite{daniel2022ipfsfriends}.

A directory on IPFS also receives a CID. The directory CID covers all files in the directory. A relative path inside the directory therefore always leads to the same file under the same directory CID. However, content stays available only while at least one IPFS node stores the content.

IPNS provides mutable names~\cite{ipfsdocsipns}. An IPNS name is the hash of a public key. The holder of the private key can publish a new CID under the name at any time. On the other hand, resolving an IPNS name needs an extra lookup before the content can be fetched.

Kubo is an IPFS implementation in Go~\cite{kubo}. A Kubo node offers a Hypertext Transfer Protocol (HTTP) application programming interface (API). The API includes commands such as \texttt{add}, \texttt{cat}, \texttt{name/publish} and \texttt{name/resolve}.

\section{Research method}\label{sec:method}

The work follows design science, where a designed artifact answers the research questions and an evaluation of the artifact gives the evidence~\cite{hevner2004design}. The study has four steps.

The first step analyses the problem. The analysis compares the assumptions of the EMF resource model about URIs with the properties of content addressing (Section~\ref{sec:background}). The comparison yields the list of departures in Section~\ref{sec:rq1-differences}.

The second step designs and builds the artifact. The artifact is the ecorefs core plugin with an EMF resource, a resource factory and a URI handler for IPFS (Section~\ref{sec:rq1}). The design also covers the strategies for cross-resource references and the cascade save (Section~\ref{sec:rq2}). After that, two Eclipse tools bring the artifact to a user interface (Section~\ref{sec:tool}).

The third step validates the functions. Automated tests and example programs check save and load round trips, mixed resource sets and cross-resource references (Sections~\ref{sec:evaluation-rq1} and~\ref{sec:evaluation-rq2}).

The fourth step measures cost and scale. A benchmark on generated models compares saves through IPFS with saves to local XMI files (Section~\ref{sec:evaluation-rq3}). Furthermore, a case study on large models of Java code follows the guidelines of Runeson and H\"ost~\cite{runeson2009case} and reports the publication of 1.04~GiB of models (Section~\ref{sec:evaluation-modisco}).

Each research question uses a different part of the evidence. The implementation and the functional tests answer RQ1. The reference strategies, the cascade save and the BPMN case study cover RQ2. The benchmark and the measurements of the case study give the numbers for RQ3. Section~\ref{sec:answers} collects the answers, and Section~\ref{sec:threats} discusses the threats to validity.

\section{Content-addressed model persistence}\label{sec:rq1}

The ecorefs core plugin adds IPFS persistence to EMF. The plugin is a Java library built with Maven for Java~11. The plugin uses the EMF Ecore library (version 2.23.0) and a Java client for the IPFS HTTP API (version 1.4.3)~\cite{javaipfsclient}.

\subsection{Architecture}\label{sec:rq1-architecture}

Figure~\ref{fig:architecture} shows the three extension points of the plugin as a Unified Modeling Language (UML) class diagram. \texttt{IPFSResourceImpl} extends the XMI resource of EMF, and \texttt{IPFSResourceFactoryImpl} creates the IPFS resources. \texttt{IPFSURIHandlerImpl} extends the default URI handler of EMF. Every extension point talks to one local Kubo node. The enumeration \texttt{ReferenceMode} selects references by CID or by IPNS name. Finally, a fourth class, \texttt{IPFSModelPersister}, provides the cascade save of Section~\ref{sec:rq2-cascade}.

Listing~\ref{lst:setup} shows the configuration of a resource set. The factory is registered for the \texttt{ipfs} and \texttt{ipns} schemes. The URI handler is added at the front of the handler list, so the handler receives IPFS URIs before the default handlers.

\subsection{Saving a model}\label{sec:rq1-save}

Figure~\ref{fig:save} shows the save interaction as a UML sequence diagram. Saving an \texttt{IPFSResourceImpl} takes three steps. First, the resource writes the XMI serialization to a temporary file. The temporary file avoids keeping a large serialized model in memory. Second, the file is added to the local Kubo node, and Kubo returns the CID. Third, the resource URI is replaced with \texttt{ipfs://} followed by the CID.

In IPNS mode, the third step differs. The resource derives a key name from the resource URI. An Ed25519 key is created when no key with the name exists. The new CID is then published under the key, and the resource URI becomes \texttt{ipns://} followed by the key identifier. The key name is kept after the first save, so later saves publish under the same name.

\subsection{Loading a model}\label{sec:rq1-load}

\texttt{IPFSURIHandlerImpl} reads models for the resource set, as shown in Figure~\ref{fig:load}. For an \texttt{ipfs://} URI, the handler removes the fragment and fetches the content with the Kubo \texttt{cat} command. For an \texttt{ipns://} URI, the handler first resolves the name to a CID. The handler also reads plain \texttt{http://} and \texttt{https://} URIs. Yet output streams for all four schemes are rejected. A model is written only through \texttt{IPFSResourceImpl.save}, because content under an existing CID cannot change.

\subsection{Differences from location-based persistence}\label{sec:rq1-differences}

The implementation shows four points where content addressing departs from the assumptions of the EMF resource model:
\begin{enumerate}
\item A new resource needs a URI before the first save, but the CID exists only after the save. The tests and examples use placeholder URIs such as \texttt{ipfs://pending}.
\item Every save in CID mode assigns a new URI to the resource. Code with a stored copy of the old URI still refers to the old version.
\item An output stream for an existing CID has no meaning. The save operation therefore writes a temporary file and adds the file to IPFS without the output streams of the URI converter.
\item File resources and IPFS resources can use one resource set configuration, because the IPFS handler accepts only IPFS and HTTP URIs. The BPMN example program loads local \texttt{.bpmn} files and IPFS resources with the same configuration.
\end{enumerate}

Figure~\ref{fig:lifecycle} summarizes the resulting lifecycle as a UML state machine. In CID mode, the URI of a resource follows the content. In IPNS mode, the URI stays stable, and the IPNS name follows the content.

\begin{figure}[tbp]
\centering
\includegraphics[width=.9\columnwidth]{figures/lifecycle.pdf}
\caption{UML state machine of the URI of an \texttt{IPFSResourceImpl}. Each state shows the URI and the effect of a later save after a change. In CID mode, the URI follows the content. In IPNS mode, the URI stays the same, and the IPNS name points to the new CID. Earlier CIDs stay readable while an IPFS node stores the content.}\label{fig:lifecycle}

\section{Cross-resource references}\label{sec:rq2}

\subsection{Version pinning by content addressing}\label{sec:rq2-pinning}

A reference to a resource on IPFS contains the CID of the target resource, for example \verb|href="ipfs://QmB...#//Person"|. The CID fixes the content of the target. When the target model changes, the changed model receives a new CID. The existing reference still resolves to the old version, as long as an IPFS node keeps the old content. Figure~\ref{fig:pinning} contrasts the two kinds of references.

\begin{figure}[tbp]
\centering
\includegraphics[width=\columnwidth]{figures/version-pinning.pdf}
\caption{References under location-based and content-addressed persistence. (a) A file path resolves to the current content at the path. (b) A CID reference resolves to the version with the given CID.}\label{fig:pinning}
\end{figure}

For models developed independently, the behavior pins a dependency in the same way as a lock file~\cite{npmpackagelock,gomodules}. A model keeps working with the version used during validation. Moreover, the adoption of a newer version becomes an explicit step.

The publication tools for partitioned models combine directories, manifests and one IPNS name (Section~\ref{sec:rq2-partitioned}).

\subsection{Cascade save}\label{sec:rq2-cascade}

In CID mode, a change to one resource requires new saves of every resource with a reference to the changed resource. \texttt{IPFSModelPersister.cascadeSave} automates the saves (Algorithm~\ref{alg:cascade}).

\begin{algorithm}
\caption{Cascade save in CID mode}\label{alg:cascade}
\begin{algorithmic}[1]
\Procedure{CascadeSave}{$r$}
\State $X \gets$ all cross-references in the resource set
\State $A \gets \{r\}$ and every resource that reaches $r$ through $X$
\State $O \gets$ empty list
\ForAll{$a \in A$}
\State \Call{Append}{$a, A, X, O$}
\EndFor
\ForAll{$q \in O$}
\State save $q$ to IPFS
\EndFor
\EndProcedure
\Statex
\Procedure{Append}{$q, A, X, O$}
\If{$q \in O$ or $q$ lies on the current path}
\State \Return
\EndIf
\ForAll{$t \in A$ with a reference from $q$ in $X$}
\State \Call{Append}{$t, A, X, O$}
\EndFor
\State append $q$ to $O$
\EndProcedure
\end{algorithmic}
\end{algorithm}

The procedure starts with the cross-references of the resource set, collected by the EMF cross referencer. From the cross-references, the procedure builds a dependency graph of the resources and collects every resource that reaches the changed resource. After that, the procedure orders the collected resources, so a resource comes after every collected resource that the resource references. The saves then follow that order. During serialization, EMF writes the current URI of the target into each reference. The rewritten references therefore point to the new CID without any text replacement. The procedure resembles a Git commit, where a changed file leads to new tree objects up to the root~\cite{chacon2014progit}.

The order matters as soon as two reference paths reach the changed resource. In the case study of Section~\ref{sec:evaluation-rq2}, \texttt{collaboration.bpmn} refers to the order process and to the payment process, while the order process also refers to the payment process. A save of the collaboration before the order process would leave the collaboration with the old CID of the order process. The dependency order saves the payment process first, the order process second and the collaboration last. An earlier version of the cascade saved a resource as soon as a reference to a saved resource appeared, and the order of the saves came from a hash set, so the outcome depended on the iteration order. In IPNS mode, \texttt{cascadeSave} saves only the changed resource. References by IPNS name resolve to the newly published CID, so the referencing resources need no new save.

Cycles need care. Resource A may refer to resource B while B refers to A. In such a cycle, one direction always refers to an outdated CID, because no order of saves satisfies both directions. A new save of A would change the CID of A again, so the cycle cannot settle. \texttt{IPFSModelPublishTool} therefore checks a partitioned model for cycles before a publication in CID mode. The tool stops with an error when the resource graph contains a cycle.

\subsection{Publishing partitioned models}\label{sec:rq2-partitioned}

Large models are often split into many resources. The MoDisco case study (Section~\ref{sec:evaluation-modisco}) uses one root resource and one resource per Java compilation unit. \texttt{IPFSVersionManifestPublisher} publishes such a model in four layers:
\begin{enumerate}
\item Each compilation-unit resource is an immutable file inside the directory of a component.
\item Each plug-in or module forms a component. The component directory is published as one IPFS directory with a component root CID. A component manifest lists the resources of the component and the dependencies of the component.
\item A project version manifest records the CID of the root model and the CIDs of shared resources. For each component, the manifest records the component root CID and the CID of the component manifest.
\item One IPNS name points to the current project version manifest. A local file records the IPNS name and the CID of the current manifest.
\end{enumerate}

The project version manifest holds the CID of the root model, the CIDs of the shared resources and one entry per component. \section{Evaluation}\label{sec:evaluation}

The evaluation uses the tests and example programs of the ecorefs repository for RQ1 to RQ3. A case study with large models complements the tests (Section~\ref{sec:evaluation-modisco}).

\subsection{Setup}\label{sec:evaluation-setup}

The measurements ran on a laptop with an Intel Core i7-1165G7 processor (four cores, eight threads, up to 4.70~GHz) and 16~GB of memory, under Ubuntu 24.04.3 with Linux 6.8.0. The Java code ran on OpenJDK 21.0.9, and the plugin is compiled for Java~11. The local IPFS node ran Kubo 0.40.1 in Docker 29.8.0 and offered the HTTP API on port 5001. The node ran in offline mode with an empty store, so the measurement covers the local store without announcements of new blocks to the public network. The plugin uses EMF Ecore 2.23.0, EMF XMI 2.16.0, EMF Common 2.21.0 and the Java client for the IPFS HTTP API 1.4.3. The tests of the core plugin run with JUnit 5.10.0, and the build uses Maven 3.8.7 with the Surefire plugin 3.1.2. The virtual machine of the benchmark runs with a fixed heap of 8~GB, and a garbage collection runs between the iterations, outside the measured region. The XMI copy of each benchmark model goes to a temporary file on an ext4 file system on a solid state disk. Each benchmark first runs three warm-up iterations and then thirty measured iterations on an otherwise idle machine. The tests measure wall-clock time with \texttt{System.nanoTime} and report milliseconds with three decimals.

\subsection{RQ1: Functional validation}\label{sec:evaluation-rq1}

An example program (\texttt{BpmnIpfsExample}) exercises the persistence layer with two BPMN models. The program saves both models to IPFS and loads the first model again by CID. The program then resolves an element of the first model through a URI fragment. The second model refers to the process of the first model with an \texttt{ipfs://} URI and a fragment.

The self-tests of the BPMN2 Modeler extension check reference parsing, command registration, bundle metadata and the documentation. An optional mode of the self-tests publishes a BPMN file to Kubo and downloads the file again. \todo{Report the output of the example program and of the self-tests with a running Kubo node.}

Large models need a stronger check than an example program. The case study of Section~\ref{sec:evaluation-modisco} therefore compares local resources with copies fetched from IPFS. EMF Compare reported no differences for eight components with 1,639 resources and 240.61~MiB of XMI, and a repeat run of the same selection gave the same result (Table~\ref{tab:compare})~\cite{emfcompare}. In addition, byte-level checks cover the merged model, the project version manifest and the partitioned root model. A traversal test counted 4,282,694 elements in the merged model and the same number in the partitioned resource set. Overall, the checks support the claim that a save to IPFS and a later load return the same model at the scale of the case study.

\subsection{RQ2: Reference evolution}\label{sec:evaluation-rq2}

The cascade test builds two resources with one object each. The object in resource A has a non-containment reference to the object in resource B. The test calls \texttt{cascadeSave} on B and measures the time for both saves. Over ten runs, the cascade save took 55~ms on average, with a median of 55~ms and a standard deviation of 2.10~ms. The measurement covers two IPFS saves of very small resources, so the time comes almost completely from the two calls to the local node. However, the test does not measure the search for cross-references separately.

Three further tests check the rewritten references. Each test builds resources with one node, saves every resource, changes the last resource and calls \texttt{cascadeSave}. After the cascade, each test fetches the stored bytes of every referencing resource from the node and checks that the reference carries the current CID of the target. The first test uses a chain of two resources. The second test uses the diamond of Figure~\ref{fig:cascade}, where the collaboration refers to the order process and to the payment process. The third test uses a chain of four resources, where the cascade save took 106~ms for four saves. All three tests pass.

The BPMN case study of the introduction uses three real BPMN files. \texttt{payment-process.bpmn} defines a payment process with three tasks. \texttt{order-process.bpmn} supports the payment process. \texttt{collaboration.bpmn} has two participants, one for the order process and one for the payment process. A test loads the three files with the BPMN 2.0 metamodel of Eclipse, saves the three resources to IPFS and then changes the name of the payment process. The cascade save took 84~ms for the three saves. Figure~\ref{fig:cascade} shows the CIDs of that run before and after the change. After the cascade, the stored collaboration carries the new CID of the order process and the new CID of the payment process, and the stored order process carries the new CID of the payment process.

\section{Discussion}\label{sec:discussion}

\subsection{Answers to the research questions}\label{sec:answers}

For RQ1, the main challenges come from the changing identity of a resource. A resource has no final URI before the first save, the URI changes with every save, and content under an existing CID cannot be overwritten. The implementation handles the challenges with placeholder URIs and with a new URI after each save. In addition, a read-only URI handler covers loading. In the example program, loading by CID and navigation by URI fragment work through the standard resource set API. A separate test loads a resource with a reference to a second resource in a fresh resource set, where the reference starts as a proxy. The first access to the reference fetches the second resource from the node and returns the object behind the proxy, so proxy resolution works across \texttt{ipfs://} references.

For RQ2, references by CID pin versions. A deliberate upgrade requires new saves along the chain of referencing resources. The cascade save automates the saves for acyclic references. IPNS names avoid the cascade but give up immutability. For the large partitioned model, component directories, manifests and one IPNS name gave a workable publication structure.

For RQ3, a save through a local Kubo node added 20 to 22~ms per model for models up to 10,000 elements, and 46~ms to 112~ms for the two largest models. The relative cost falls from about 31 times the XMI time at 100 elements to 1.4 times at 500,000 elements, because the added time comes mostly from a fixed cost per call. Loading from IPFS took 1.1 to 1.4 times the time of loading a local XMI file. The measured costs appear acceptable for interactive editing, where a save of a model with 10,000 elements stays under 26~ms. Nevertheless, remote nodes and IPNS resolution still need measurement.

\subsection{Limitations}\label{sec:limitations}

The approach loads each resource as a whole. Database-backed persistence can load parts of a model on demand~\cite{pagan2011morsa,daniel2017neoemf}, but the IPFS layer cannot. The approach also offers no query support comparable to Object Constraint Language (OCL) queries inside a database~\cite{omg2014ocl,daniel2016mogwai}. Furthermore, IPNS resolution needs an extra lookup and can take longer than direct CID access. In CID mode, a change to a leaf resource causes saves along the whole dependency chain. Cyclic references always leave one outdated CID. Published models stay available only while at least one node stores the content.

\subsection{Threats to validity}\label{sec:threats}

The main threat to internal validity comes from the environment of the measurement. Garbage collection can affect single iterations, and a node that announces new blocks to the public network competes with the next measurement. The benchmark reduces both risks with a fixed heap of 8~GB, a collection between the iterations, a node in offline mode with an empty store, three warm-up iterations, thirty measured iterations per model size and a paired statistical test. Earlier runs on a busy machine and with an online node gave times up to four times higher, so the reported run used an otherwise idle machine. The cascade tests also cover small resources only.

External validity is limited by the setup. The benchmarks use one generated metamodel and a local Kubo node. The case study covers Java code models only. Therefore, results may differ for other metamodels, for remote IPFS nodes and for the public IPFS network.

For construct validity, the wall-clock time of single save and load calls stands for the cost of persistence. In addition, the EMF Compare check covered eight components and left out the shared resources.

\section{Related work}\label{sec:related}

\subsection{Scalable model persistence}\label{sec:related-persistence}

Kolovos et al. propose a research roadmap for scalability in MDE, covering large models, collaborative modeling, and scalable queries and transformations~\cite{kolovos2013roadmap}. Morsa stores large models in a non-relational (NoSQL) database and loads model parts on demand~\cite{pagan2011morsa}. The journal version adds incremental store to the Morsa repository~\cite{pagan2015repository}. Neo4EMF provides a scalable persistence layer for EMF~\cite{benelallam2014neo4emf}. NeoEMF offers several database back ends in one framework, because a single data store rarely suits all modeling activities~\cite{daniel2017neoemf}. Mogwaï translates OCL queries to Gremlin and runs the queries inside the database~\cite{daniel2016mogwai}. Scheidgen compares model representations such as XMI trees and relational data in CDO~\cite{scheidgen2013reference}. The CDO model repository stores and versions models in a central repository with relational, NoSQL or in-memory databases~\cite{cdo}. The approaches identify model elements inside a store. In every case, the identifiers stay stable while the content changes.

\subsection{Model repositories and versioning}\label{sec:related-versioning}

ReMoDD collects model-driven development artifacts for research and education~\cite{france2007remodd}. Di Rocco et al. discuss model repositories for collaborative modeling, tool interoperability and model reuse~\cite{dirocco2015repositories}. EMFStore versions EMF models with operation-based change tracking, conflict detection and merging~\cite{koegel2010emfstore}. Altmanninger et al. survey version control systems for models with a focus on three-way merging~\cite{altmanninger2009survey}. Brosch et al. introduce the research challenges of model versioning~\cite{brosch2012versioning}. Model comparison supports model composition and transformation testing~\cite{kolovos2006comparison}, and EMF Compare compares and merges models of any metamodel~\cite{emfcompare}. Hawk indexes large collections of models kept in version control systems~\cite{barmpis2013hawk}. A mapping study classifies approaches to collaborative model-driven software engineering~\cite{franzago2018collaborative}. The versioning approaches record or compute differences between versions. Content addressing instead gives each version a fixed identifier derived from the content.

\subsection{Content-addressed storage outside MDE}\label{sec:related-content}

Content addressing is established in several areas. Venti enforced write-once archival storage with hash-based block identifiers~\cite{quinlan2002venti}. Git is a content-addressable file system~\cite{chacon2014progit}. Nix computes unique component paths from cryptographic hashes, so several versions of a component can coexist~\cite{dolstra2004nix}. Software Heritage treats software source code as a digital object with a need for preservation~\cite{dicosmo2017heritage}. On IPFS, InterPlanetary Wayback stores and replays web archives~\cite{kelly2016wayback}. Other work combines IPFS with blockchains for document version control~\cite{nizamuddin2019document} and for a peer-to-peer file system with content service providers~\cite{chen2017improved}. A survey compares IPFS with other decentralized data networks~\cite{daniel2022ipfsfriends}. However, none of the reviewed approaches applies content addressing to EMF models or to references between model resources.

\subsection{Dependency management and reproducibility}\label{sec:related-dependencies}

Package managers record exact dependency versions. The npm lock file describes the exact dependency tree, so later installations can create identical trees~\cite{npmpackagelock}. Go modules record dependency versions and checksums~\cite{gomodules}. Studies show the risks of dependency updates in software ecosystems~\cite{cox2019dependencies,decan2019ecosystems}. Reproducible builds check whether binaries correspond to the source code~\cite{lamb2022reproducible}. Likewise, version pinning by CID applies the same idea to models, and a cascade save plays the role of a deliberate dependency upgrade.

\section{Conclusion}\label{sec:conclusion}

The paper studied EMF model persistence on IPFS. An EMF resource implementation saves models to IPFS and assigns the new CID to the resource URI. A URI handler also loads models by CID or IPNS name. References by CID pin exact versions, and a cascade save updates referencing resources in CID mode. IPFS support was also added to the Eclipse BPMN2 Modeler and to the generated BPMN2 tree editor.

With a local Kubo node, a save through IPFS added 20 to 22~ms per model for models up to 10,000 elements, and the relative cost fell from about 31 times the XMI time at 100 elements to 1.4 times at 500,000 elements. The MoDisco case study published 1.04~GiB of Java models as 6,933 resources. EMF Compare found no differences for eight components with 1,639 resources.

Future work includes remote IPFS nodes, a shared network file system as a further baseline and measurements of IPNS resolution. The cascade save also needs tests with longer reference chains and with several reference paths to one resource.
